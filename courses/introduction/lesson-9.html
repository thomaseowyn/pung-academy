Debugging & Problem Solving

    Learning material

    Everyone's code breaks

    You are eight chapters in, which means you have already seen a respectable number of errors. Here is the thing nobody tells beginners early enough: that never stops. Experienced programmers do not write code that works first time. They write code that breaks, and then they are quick and unbothered about fixing it.

    The difference is method. This chapter is about that method — which is why it comes before the final project rather than after it.

    Reading error messages

    Python's errors look intimidating and are actually generous. Take this one apart: 

    Traceback (most recent call last):
  File "shopping.py", line 7, in <module>
    total = price * quantity
TypeError: can't multiply sequence by non-int of type 'str'
    • Read the last line first. TypeError is the family; the sentence after it is the actual complaint.
    • Then the file and line number. Line 7 of shopping.py. That is where to look.
    • Then the code shown. Python quotes the offending line back to you.

    Translated into English, that message says: you tried to multiply two pieces of text. Almost certainly quantity came from input() and was never converted with int().

    The errors you will meet most

    • SyntaxError — Python cannot read the code. Missing colon, bracket or quote.
    • IndentationError — the spacing does not line up.
    • NameError — you used a name that does not exist. Usually a typo, or a variable used before it was created.
    • TypeError — an operation applied to the wrong type, like adding a number to a string.
    • ValueError — right type, impossible value. int("hello").
    • IndexError / KeyError — asking a list or dictionary for something that is not there.
    • ZeroDivisionError — exactly what it says.
    Tip

    If a message genuinely means nothing to you, paste the last line into a search engine. Thousands of people have hit the same error. This is normal practice, not cheating.

    The three kinds of bug

    1. Syntax errors. The program will not start. Annoying, but the easiest kind — Python points at the line.
    2. Runtime errors. The program starts and then crashes. Python still tells you where and why.
    3. Logic errors. The program runs perfectly and gives the wrong answer. Nothing is reported, because as far as Python is concerned nothing went wrong. These are the hard ones.

    An example of the third kind:

    grades = [80, 90, 70]
total = 0

for grade in grades:
    total = grade          # should be total += grade

average = total / len(grades)
print(average)             # prints 23.33, not 80.0

    No error, no crash, no warning — just a quietly wrong number. This is why testing matters.

    Debugging strategies

    1. Print what you believe

    The oldest and still most useful technique. If you think a value is one thing, print it and check. 

    for grade in grades:
    print("grade is", grade, "and total is", total)   # temporary
    total = grade

    Run that and the bug is visible instantly: total tracks the current grade rather than accumulating. Delete the print once you have your answer.

    2. Narrow it down

    You do not need to find the bug by staring at all forty lines. Find the last line you are certain is correct, and the first line you are certain is wrong. The fault is between them. Print in the middle and halve the search again.

    3. Change one thing at a time

    Change three things, rerun, and it works — which fix worked? You have no idea, and you have possibly introduced a new bug that is currently hidden. One change, one run.

    4. Explain it out loud

    Describe your code line by line to somebody — or to a wall, or a rubber duck. The traditional name really is rubber duck debugging. Saying "and then this adds the grade to the total" forces you to check whether it does, and that is usually the moment you see it.

    5. Check your assumptions about types

    An enormous share of beginner bugs are a string where a number was expected. print(type(x)) settles it in one line.

    Testing programs

    Testing is deliberately trying to make your program fail, before someone else does it by accident. For any program, try:

    • A normal case. The thing you expect. Age 25.
    • Edge cases. The boundaries. Age exactly 18. An empty list. Zero.
    • Invalid input. Letters where a number belongs. Nothing at all. A negative age.

    Take the grade calculator from Chapter 5. A score of 85 gives a B — fine. But what about exactly 80? Exactly 90? 0? 101? Minus 5? Each of those is a real question about whether your conditions are right, and the boundaries are where the bugs live.

    Note

    Professional projects automate this with test frameworks that run hundreds of checks in seconds. The thinking is identical to what you are doing by hand here.

    Breaking problems into smaller pieces

    "Build a task manager" is not a problem you can solve. It is a project. Split it until each piece is something you already know how to do: 

    Build a task manager
├── Store the tasks              -> a list (Chapter 7)
├── Show a menu                  -> print (Chapter 2)
├── Repeat until they exit       -> a while loop (Chapter 6)
├── Read their choice            -> input (Chapter 3)
├── Do the right thing           -> if / elif (Chapter 5)
└── Each action                  -> a function (Chapter 8)
    ├── add a task               -> append
    ├── show tasks               -> a for loop
    └── mark one complete        -> change a dictionary value

    Nothing in that tree is beyond you. That is what decomposition buys: an impossible-looking project becomes eight small tasks you have already practised.

    Thinking like a programmer

    The habits worth taking with you:

    • Be precise about what is actually happening, not what you meant to happen. The computer did exactly what you wrote.
    • Work in small steps. Write a few lines, run them, confirm, continue. Do not write ninety lines and then press run.
    • Assume the bug is yours. It is almost never Python. It is nearly always a typo, a type, or an assumption.
    • Get comfortable being stuck. Being stuck is the job, not a sign you are unsuited to it.

    Worked example — debugging in practice

    This should print the average of the grades. It does not.

    grades = [80, 90, 70]
total = 0

for grade in grades
    total = grade

average = total / len(grade)
print("Average: " + average)

    Fixing it one error at a time, exactly as you should:

    1. SyntaxError on the for line — the colon is missing. Add it, rerun.
    2. NameError: name 'grade' is not defined from len(grade) — the list is called grades. Fix, rerun.
    3. TypeError on the print — you cannot join a string to a number with +. Use a comma, rerun.
    4. Now it runs and prints 23.33. No error, so this is a logic error: total = grade should be total += grade. 
    grades = [80, 90, 70]
total = 0

for grade in grades:
    total += grade

average = total / len(grades)
print("Average:", average)      # Average: 80.0

    Four faults, four separate fixes, each confirmed by rerunning. That patience is the entire skill.

    Without writing code, describe the steps to find the second largest number in a list. Careful: keeping two variables and updating them in the wrong order is a classic logic error. What happens if the list has only one item?
