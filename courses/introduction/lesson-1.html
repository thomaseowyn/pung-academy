    What programming actually is

    A computer is astonishingly fast and completely unimaginative. It will do exactly what you tell it, in exactly the order you tell it, several billion times a second — and it will never once work out what you meant. Programming is the craft of writing instructions precise enough for something that literal.

    That is the whole job. Not memorising syntax, not knowing every function by heart. Taking a task you understand, breaking it into steps small enough that nothing is left to interpretation, and writing those steps down in a language the machine can read.

    Note

    People often say programming is like giving directions. The better comparison is giving directions to someone who has never been outside, cannot see, and will walk into a wall rather than assume you meant "turn before the wall".

    What a program is

    A program is a saved list of instructions. When you run it, the computer works through the list from top to bottom and does what each line says. Your web browser is a program. So is the calculator on your phone, and so is the three-line file you are going to write in the next chapter.

    Programs are written in a programming language — a limited, unambiguous vocabulary designed so that every statement has exactly one meaning. This course uses Python, because it reads closer to English than most languages and gets out of your way while you are learning the ideas underneath.

    Algorithms: the plan before the code

    An algorithm is a finite, ordered set of steps that solves a problem. That is a formal-sounding definition for something you already do constantly. A recipe is an algorithm. Long division is an algorithm. The route you take to school is an algorithm.

    Three things make a set of steps an algorithm rather than a vague intention:

    • It is ordered. Step 3 happens after step 2. Swapping them changes the outcome.
    • It is unambiguous. Every step means exactly one thing. "Add a bit of salt" is not an algorithm step. "Add 5 grams of salt" is.
    • It finishes. There is a point at which the task is done and you stop.

    Why this matters more than the code

    Beginners usually believe their problem is that they do not know enough syntax. Almost always, the real problem is that they have started typing before they know what the steps are. If you cannot describe the solution in plain language, no amount of Python will rescue you — you will just produce a very precise description of a plan you have not made yet.

    Tip

    When you get stuck later in this course, the fix is nearly always to stop writing code and describe, out loud, what should happen step by step. The bug is usually in the plan.

    Pseudocode: writing the plan down

    Pseudocode is your algorithm written in plain language, but structured like a program. It is not a real language and no computer runs it. It exists so you can think about the steps without also fighting the rules of a language.

    Say you want to work out whether someone is old enough to vote: 

    ASK the person for their age
STORE the answer as age

IF age is 18 or more
    SHOW "You can vote"
OTHERWISE
    SHOW "You are too young to vote"

    There is no Python here at all, and yet the logic is completely settled. Every decision that matters has been made. Turning this into real code later becomes translation rather than problem solving — and that is a much easier job.

    How to write useful pseudocode

    • Use one line per step.
    • Indent the steps that only happen in a particular case, as with the two SHOW lines above.
    • Write verbs you could actually carry out: ASK, STORE, ADD, SHOW, REPEAT, IF.
    • Do not worry about being neat. Pseudocode is a thinking tool, not a deliverable.
    Small exercise

    Before reading on, write pseudocode for making a cup of tea. Then look at it again and ask: did you say what happens if there is no water in the kettle? A computer would need to be told.

    Flowcharts: the plan as a picture

    A flowchart is the same idea drawn instead of written. It is useful when a problem has several branches and you want to see all the paths at once. The shapes are conventional:

    • Oval — where the program starts or stops.
    • Rectangle — an action, such as a calculation.
    • Parallelogram — input or output, such as asking a question or showing a result.
    • Diamond — a decision, with one arrow out for yes and one for no.

    The voting example as a flowchart, sketched in text:

            ( Start )
             |
     [ Ask for age ]
             |
      < age >= 18 ? >
        /         \
     yes           no
      |             |
[ "You can vote" ] [ "Too young" ]
        \           /
         ( Stop )

    Notice that both branches come back together and end in one place. A program with a path that simply stops halfway, leaving the person with no answer, is almost always a program with a bug.

    Putting it together

    The working order for the rest of this course, and honestly for the rest of your programming life, is:

    1. Understand the problem. Say it back in your own words.
    2. Work out the steps. Pseudocode or a flowchart.
    3. Translate the steps into code.
    4. Run it, see what actually happens, and fix the difference.

    Beginners skip straight to step 3 and then wonder why step 4 takes all evening. You now know the trick, which puts you ahead of where most people start.
