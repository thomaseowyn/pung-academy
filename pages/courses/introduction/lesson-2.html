    Learning material

    Writing your first program

    Here is a complete, working Python program. One line long, and it genuinely counts. 

    print("Hello, world!")
    Output 
    Hello, world!

    Take it apart, because every piece matters:

    • print is the name of a built-in function — a piece of work Python already knows how to do. This one displays something on screen.
    • The brackets ( ) are how you call a function. They hold whatever you are giving it to work with.
    • The quotation marks mark the start and end of some text. Without them Python would think Hello was the name of something you had defined.
    Note

    "Hello, world" is the traditional first program in almost every language. It is not there to teach you anything about text — it is there to prove your setup works before you write anything harder.

    Syntax: the rules of the language

    Syntax is the set of rules about how code must be written. English has syntax too — "programming is fun" is a sentence and "fun programming is" is a mess — but English readers cope with mistakes. Python does not. One missing bracket and it refuses to run anything at all.

    The rules you meet immediately:

    • Brackets come in pairs. Every ( needs a ).
    • Quotes come in pairs, and must match. "Hello" and 'Hello' are both fine. "Hello' is not.
    • Spelling and case matter. print works; Print and prnt do not.
    • Indentation is meaningful. In most languages leading spaces are decoration. In Python they define which lines belong to which block, as you will see in Chapter 5.

    Comments

    A line starting with # is a comment. Python ignores it completely. Comments are notes to humans — usually to you, in three weeks, when you have forgotten why you did something. 

    # Greet the person using the program
print("Hello, world!")   # this bit runs; the note after the hash does not
    Tip

    Write comments about why, not what. # add 1 to counter tells a reader nothing they could not see. # skip the header row tells them something real.

    Running a program

    Writing code and running code are two separate acts. You type instructions into a file and save it — commonly with a .py ending, such as hello.py — and then you ask Python to execute that file.

    Python reads your file from the top and performs each line in turn. This program prints three lines, in this order and no other: 

    print("First")
print("Second")
print("Third")
    Output 
    First
Second
Third

    That top-to-bottom march is the single most important thing to hold in your head. When a program misbehaves, tracing which line ran when will find the fault more often than staring at it will.

    Understanding errors

    You are going to see a great many error messages. This is not a sign that something has gone wrong with you; it is the normal texture of the work. Professionals see errors constantly. The difference is that they read them.

    Errors come in two broad families.

    1. Syntax errors — Python cannot read your code

    The program does not start at all. Something is written in a way Python cannot parse. 

    print("Hello, world!"
    Output 
      File "hello.py", line 1
    print("Hello, world!"
         ^
SyntaxError: '(' was never closed

    Read it backwards, because the useful part is at the bottom. SyntaxError tells you the family. The message names the exact fault. The line number and the little ^ marker tell you where. Every piece of that is a gift; none of it is scolding you.

    2. Runtime errors — Python understood, but could not do it

    The program starts, runs for a while, and then hits something impossible. 

    print("The answer is")
print(10 / 0)
    Output 
    The answer is
Traceback (most recent call last):
  File "maths.py", line 2, in <module>
    print(10 / 0)
ZeroDivisionError: division by zero

    Notice that The answer is was printed before the crash. That is the top-to-bottom march again, and it is a clue: everything before the failing line did run.

    Careful

    There is a third kind of problem that produces no error at all: the program runs perfectly and gives the wrong answer. That is a logic error, and it is the hardest sort to find, because nothing tells you it happened. Chapter 9 is largely about these.

    Debugging basics

    Debugging is finding and fixing the difference between what your program does and what you intended. A method that works from your first day:

    1. Read the whole message. Do not skim to the colour red and panic. The last line names the problem.
    2. Go to the line number. If nothing looks wrong there, check the line above — an unclosed bracket is reported on the line where Python gave up, not where you slipped.
    3. Change one thing. Then run it again. Changing five things at once means you will not know which fixed it.
    4. Print what you are unsure about. If you do not know what a value is at some point, print it and find out.
    Small exercise

    Each of these is broken in exactly one way. Name the fault in each before checking the next chapter's material: 

    print("Line one)
Print("Line two")
print "Line three"

    In order: an unclosed quote, a capital P where Python expects lowercase, and missing brackets around the text.
