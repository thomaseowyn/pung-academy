Task Management System

    Introduction

    What this project pulls together

    Fourteen modules, one project: a Task Management System where users sign up, create tasks, mark them complete, and only ever see their own. This chapter walks through the same design process a real team would follow — requirements, schema, API, security, testing, and a deployment plan — with every decision pointing back to the module that taught it.

    Learning material

    Requirements and user stories

    Following Module 1, "users need to manage their tasks" becomes concrete requirements before anything is designed:

    • Functional: a user can register, log in, create a task, mark it complete, edit it, delete it, and list their own tasks.
    • Non-functional: a user can only ever see and modify their own tasks; the API responds in under 300ms for a normal request.

    A user story frames each requirement from the user's side:

    As a signed-in user,
I want to mark a task as complete,
so that I can track what's actually done.

    System design and database schema

    Module 6's relational design, applied to this project:

    users                        tasks
+----+----------+----------+ +----+---------+-------+----------+---------+
| id | email    | password | | id | user_id | title | due_date | is_done |
|    |          | _hash    | |    |         |       |          |         |
+----+----------+----------+ +----+---------+-------+----------+---------+

    tasks.user_id is a foreign key referencing users.id — every task belongs to exactly one user, which is what makes "only see your own tasks" enforceable at the database level, not just trusted from the frontend.

    REST API design

    Module 7 and Module 8's conventions, applied to this schema:

    POST   /auth/register        # create an account
POST   /auth/login           # get a session/token (Module 9)
GET    /tasks                # list the current user's tasks
POST   /tasks                # create a task
PATCH  /tasks/{id}           # update a task
DELETE /tasks/{id}           # delete a task
    Frontend → API (auth + routing) → Service (business logic) → Database

    Every request from Module 8's layered flow, now applied to a real, complete feature.

    Authentication, CRUD, and validation

    Module 9's password hashing and session/token issuance protect /auth/*. Every /tasks endpoint requires a valid session and checks (Module 9's authorization, not just authentication) that the task being modified actually belongs to the requesting user. Module 8's validation rejects a task with no title before it ever reaches the database.

    Testing and error handling

    Module 11's pyramid, applied here: unit tests for the service functions (does complete_task() correctly flip is_done?), integration tests against a real test database (does creating a task actually persist it?), and a handful of end-to-end tests for the critical paths (register → log in → create a task). Module 7 and Module 10's error handling returns clear 400s for bad input and 403s for accessing someone else's task — never a silent failure.

    Architecture, Git workflow, and documentation

    A monolith (Module 12) is the right starting architecture here — one small team, no proven independent-scaling need yet. Module 2's branch-per-feature, reviewed-pull-request workflow governs how the code actually gets written; Module 14's API documentation describes every endpoint above for whoever builds the frontend against it.

    Deployment plan

    Module 13's pipeline: push → automated build → automated test suite → deploy, containerised with Docker, configuration read from environment variables (Module 8 and Module 10), served over HTTPS (Module 10), with basic logging in place from day one so a production issue is visible before a user has to report it.

    Summary

    What this project demonstrates

    • A requirement, traced all the way through: schema (Module 6) → endpoint (Module 7) → service (Module 8) → auth check (Module 9) → test (Module 11) → deployment (Module 13).
    • Authorization enforced at the data layer, not just trusted from the frontend.
    • An architecture and process chosen to fit this project's actual size — not the biggest, most impressive option available.
