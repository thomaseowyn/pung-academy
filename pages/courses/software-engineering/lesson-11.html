Module 11

Testing & Debugging

    Introduction

    What you'll learn in this module

    You now have a working, secured backend. This module covers proving it actually works — and keeps working — with unit, integration, and end-to-end tests, plus the debugging skills to track down what went wrong when it doesn't.

    Learning material

    Why testing matters

    Without tests, "does this still work?" can only be answered by manually clicking through the application after every change — slow, easy to skip, and easy to miss an edge case. Tests turn that question into something a computer can answer in seconds, every single time.

    Unit, integration, and end-to-end testing

    End-to-end — fewest, slowest, closest to real usage Integration — fewer, checks real pieces working together Unit — many, fast, checks one small piece in isolation

    Most tests should be fast unit tests; end-to-end tests are valuable but expensive, so there are usually far fewer of them.

    • Unit tests check one small piece of code in isolation, usually with dependencies mocked.
    • Integration tests check that real pieces work together — code plus an actual database, for instance.
    • End-to-end (E2E) tests check a full real user flow, often through the actual UI, closest to how a real person experiences the app.

    Test cases and assertions

    A test calls the code being tested, then asserts the result is what's expected — if it isn't, the test fails loudly instead of the bug slipping through silently. 

    def add(a, b):
    return a + b

def test_add():
    assert add(2, 3) == 5
    assert add(-1, 1) == 0

    Mocking

    A mock is a fake, controllable stand-in for a real dependency — a database, an external API, the current time — so a unit test can check your code's own logic without needing that real (slow, unreliable, or costly) dependency to actually run.

    Debugging techniques and stack traces

    When something fails, a stack trace shows the exact chain of function calls that led to the error — read it from the bottom up: the last line is usually where the actual error occurred, with the calls that led there above it.

    Logging and regression testing

    Logging records what a running program actually did, which is often the only visibility you have into a production issue you can't reproduce locally. A regression test is a test written specifically after fixing a real bug, so that exact bug can never silently come back.

    Test-driven development (TDD)

    TDD inverts the usual order: write a failing test for behaviour that doesn't exist yet (Red), write the minimum code to make it pass (Green), then clean up the implementation with a passing test as a safety net (Refactor) — then repeat.

    Common mistakes

    Common mistakes

    • Only testing the "happy path" that works, never the edge cases (empty input, negative numbers, missing fields) that actually break things.
    • Writing tests so tangled with implementation details that any refactor breaks them, even when behaviour didn't actually change.
    • Fixing a production bug without adding a regression test, leaving the door open for the exact same bug to return.
    Best practices

    Best practices

    • Write far more unit tests than end-to-end tests — fast feedback matters more than perfect realism for most checks.
    • Test edge cases deliberately: empty input, boundary values, invalid data — not just the expected case.
    • When you fix a real bug, add a test that would have caught it.
    Summary

    Key takeaways

    • Unit tests are fast and isolated; integration tests check real pieces together; E2E tests check a full real flow.
    • An assertion states what must be true, failing loudly the instant it isn't.
    • Mocks stand in for real dependencies so unit tests stay fast and isolated.
    • TDD's Red-Green-Refactor cycle writes the test before the code that satisfies it.
