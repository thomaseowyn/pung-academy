Module 14

Professional Software Development

    Introduction

    What you'll learn in this module

    Everything so far has been technical. This module covers what turns technical skill into professional practice: working inside a team, reviewing and being reviewed, documenting decisions, estimating honestly, and navigating a codebase you didn't write — the last module before applying everything in a final project.

    Learning material

    Working in a development team

    Professional software is almost never built alone. Module 2's Git workflow (branches, pull requests) and Module 1's Agile process exist specifically to let a team work on the same codebase without constantly colliding with each other.

    Code reviews and pull requests

    A code review is a second set of eyes before a change merges — catching bugs, design issues, and unclear code the author is too close to see, and spreading knowledge of the change across the team. A good pull request description explains why, not just what — the same principle Module 2 applied to individual commit messages.

    Issue tracking and Agile workflow

    Work is usually tracked as discrete issues — a bug report, a feature request — organised into sprints (Module 1), so a team always has a shared, visible picture of what's being worked on and what's next.

    Writing technical and API documentation

    Documentation is a message to a future reader — often a future version of yourself — who won't have the context you have right now. API documentation specifically describes each endpoint (Module 7): its method, URL, parameters, and what it returns, so someone can use it without reading the implementation. 

    ## POST /tasks
Creates a new task.

**Body:** { "title": string }
**Returns:** 201 Created, the new task object
**Errors:** 400 if title is missing

    Project estimation

    Estimating how long work will take is genuinely hard and often wrong — the honest professional habit is breaking large, vague work into smaller, concrete pieces (closer to Module 1's requirements gathering) before estimating, and revisiting estimates as real information arrives, rather than treating an early guess as a fixed promise.

    Debugging production issues

    A production bug should be reproduced first (locally, or with logs from Module 11), then traced backward from there — not guessed at. This is slower than it feels like it should be, but a fix you can't verify is just a hope.

    Working with existing codebases

    Most professional work happens inside code you didn't write. Read before you change: understand the existing patterns (Module 5's principles are often already in use, even if nobody wrote them down), and prefer small, well-understood changes over large unfamiliar rewrites.

    Building a professional GitHub portfolio

    A public GitHub profile with a few genuinely finished, well-documented projects — clear READMEs, sensible commit history (Module 2), maybe a small test suite (Module 11) — says more to someone hiring than a large number of abandoned, undocumented repositories.

    Common mistakes

    Common mistakes

    • Treating code review feedback as personal criticism rather than a normal, expected part of shipping quality code.
    • Rewriting a large chunk of an unfamiliar codebase before actually understanding why it was built that way.
    • Estimating a vague task without breaking it down first, then treating that rough guess as a hard deadline.
    Best practices

    Best practices

    • Write pull request descriptions that explain the reasoning, not just a summary of the diff.
    • Break vague work into concrete pieces before estimating it.
    • Reproduce a bug reliably before attempting to fix it — a fix you can't verify isn't a fix yet.
    • Read and understand existing code's patterns before changing them.
    Summary

    Key takeaways

    • Code review catches what the author can't see and spreads knowledge across the team — not a gate to resent.
    • Good documentation and PR descriptions explain why, not just what.
    • Estimate concrete, broken-down work — and revisit estimates as real information arrives.
    • Reproduce, then trace, then fix — in that order, for any real bug.
