Module 12

Software Architecture

    Introduction

    What you'll learn in this module

    Every module so far worked at the level of one function, one endpoint, one test. This module zooms out to how a whole system is organised — monoliths vs. distributed systems, layered architecture and MVC, and the trade-offs behind each choice.

    Learning material

    What software architecture means

    Architecture is the set of high-level decisions about how a system's major pieces are organised and how they communicate — decisions that are expensive to change later, unlike most day-to-day code changes.

    Monolith vs. distributed systems

    A monolith is one deployable unit — simpler to build, test, and deploy, especially early on, but it scales and can fail as a whole. A distributed system (microservices) splits functionality into independently deployable services — better independent scaling and team autonomy, at the cost of real operational complexity: network calls between services, and debugging across all of them.

    Monolith
    (one deployable unit)     vs. Service A Service B Service C

    Microservices trade simplicity for independent scaling and deployment of each piece.

    Layered architecture and MVC

    A layered architecture separates presentation, business logic, and data access — the same idea Module 8 applied to a backend. MVC (Model-View-Controller) names this pattern explicitly: the Model holds data and business rules, the View renders what the user sees, and the Controller handles input and coordinates between them.

    Presentation (View) Business logic (Controller / Model) Data access (Database)

    Service-oriented and modular architecture

    Even inside a monolith, code can be organised into independent modules with clear boundaries (Module 3's modular programming, at the scale of a whole application) — getting some of microservices' organisational clarity without the full operational cost of splitting into separate deployed services.

    Scalability, maintainability, and reliability

    • Scalability — handling growing load by adding resources.
    • Maintainability — how easily the system can be understood and safely changed.
    • Reliability — how consistently the system behaves correctly, including when parts of it fail.

    Architecture trade-offs

    Every architectural choice trades one of these against another. A single database is simple and maintainable but limits independent scaling. Splitting into services scales independently but costs reliability guarantees (more moving parts, more ways for one piece to fail) and maintainability (more places to understand). There is no universally "correct" architecture — only one that fits the actual requirements (Module 1) and constraints in front of you.

    Common mistakes

    Common mistakes

    • Choosing microservices for a small, early-stage project because it seems more "serious," rather than because a real scaling need exists (Module 5's YAGNI, applied to architecture).
    • Letting layers blur together — business logic leaking into the presentation layer, or the data layer knowing about HTTP.
    • Treating an architecture decision as permanent and never revisiting it as real requirements and scale change.
    Best practices

    Best practices

    • Start with the simplest architecture that satisfies today's actual requirements, and revisit it as real bottlenecks appear.
    • Keep layer boundaries clean — presentation, business logic, and data access shouldn't know unnecessary details about each other.
    • When splitting out a service, do it for a measured reason (an independent scaling need, a team boundary), not by default.
    Summary

    Key takeaways

    • A monolith is simpler early on; distributed systems scale and deploy independently at the cost of operational complexity.
    • Layered architecture (and MVC specifically) separates presentation, logic, and data.
    • Scalability, maintainability, and reliability are constantly traded off against each other.
    • Choose architecture based on actual, current requirements — not out of habit or hypothetical future scale.
