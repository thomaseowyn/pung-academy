Module 6

Databases & SQL

    Introduction

    What you'll learn in this module

    By the end of this module you'll understand how relational databases organise data into related tables, know what a primary and foreign key actually do, and be able to read and write the core SQL every backend relies on: SELECT, INSERT, UPDATE, DELETE, WHERE, ORDER BY, and JOIN.

    Learning material

    Relational databases: tables, rows, columns

    A relational database stores data in tables — each table a grid of rows (individual records) and columns (named fields every row has). A users table might have columns id, name, and email, with one row per actual user.

    Primary and foreign keys, relationships

    A primary key uniquely identifies each row in its own table (usually an auto-incrementing id). A foreign key is a column in one table that stores another table's primary key value, creating a link between them. 

    users                    orders
+----+-------+           +----+---------+--------+
| id | name  |           | id | user_id | total  |
+----+-------+           +----+---------+--------+
| 1  | Alex  |           | 1  | 1       | 42.50  |
| 2  | Bo    |           | 2  | 1       | 15.00  |
+----+-------+           | 3  | 2       | 99.99  |
                          +----+---------+--------+

# orders.user_id is a foreign key referencing users.id

    Normalization

    Normalization splits data across related tables so each fact lives in exactly one place. Without it, a customer's address copy-pasted into every one of their order rows becomes inconsistent the moment they move and only some copies get updated. With it, the address lives once, in the customers table, and every order just references that customer.

    CRUD: SELECT, INSERT, UPDATE, DELETE

    -- Create
INSERT INTO users (name, email) VALUES ('Alex', 'alex@example.com');

-- Read
SELECT name, email FROM users WHERE id = 1;

-- Update
UPDATE users SET email = 'new@example.com' WHERE id = 1;

-- Delete
DELETE FROM users WHERE id = 1;

    Almost every backend feature, underneath, is some combination of these four operations — CRUD — against one or more tables.

    WHERE, ORDER BY, GROUP BY

    • WHERE — filters which rows are included.
    • ORDER BY — sorts the results (add DESC for descending).
    • GROUP BY — collapses rows sharing a value into one summary row, usually paired with a function like COUNT() or SUM().
    SELECT user_id, COUNT(*) AS order_count
FROM orders
GROUP BY user_id
ORDER BY order_count DESC;

    JOINs

    A JOIN combines rows from two tables based on a matching column, so a single query can pull related data from both at once instead of two separate lookups. 

    SELECT users.name, orders.total
FROM orders
JOIN users ON users.id = orders.user_id;

    Indexes and transactions

    An index is an extra structure the database maintains on a column so it can find matching rows without scanning the whole table — the database equivalent of a book's index. A transaction groups several changes so they either all succeed together or all fail together — if transferring money involves both subtracting from one account and adding to another, a transaction guarantees you never end up doing only one half.

    Database design for applications

    Designing a schema starts from the same requirements-gathering habit from Module 1: what real-world things does the application need to track (users, orders, products), and how do they relate to each other? Those relationships become foreign keys; the things themselves become tables.

    Common mistakes

    Common mistakes

    • Running an UPDATE or DELETE without a WHERE clause — this affects every single row in the table.
    • Duplicating the same fact (like a customer's name) across many rows instead of storing it once and referencing it by foreign key.
    • Forgetting an index on a column that's searched or joined on constantly, causing the database to scan the entire table every time.
    Best practices

    Best practices

    • Always write and check your WHERE clause before running UPDATE/DELETE, especially in production.
    • Normalize data that's genuinely shared and could change (customer details), and design foreign keys around real relationships.
    • Wrap multi-step changes that must succeed or fail together in a transaction.
    Summary

    Key takeaways

    • Relational databases store data in related tables; primary keys identify rows, foreign keys link them across tables.
    • CRUD (SELECT/INSERT/UPDATE/DELETE) covers almost every operation a backend performs on data.
    • WHERE filters, ORDER BY sorts, GROUP BY summarises, and JOIN combines data across tables.
    • Normalization avoids duplicated, inconsistent data by keeping each fact in exactly one place.
