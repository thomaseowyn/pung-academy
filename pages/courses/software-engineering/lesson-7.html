Module 7

APIs & HTTP

    Introduction

    What you'll learn in this module

    This module explains how one program talks to another over the internet: client-server architecture, the request/response cycle, HTTP methods and status codes, and the REST conventions most APIs follow — the foundation Module 8's backend development builds directly on.

    Learning material

    Client-server architecture

    A client (a browser, a mobile app, another backend service) always initiates: it sends a request to a server, which processes it and sends back a response. The server never contacts the client first in this model.

    Client → Server → Database

    Request flows client → server → database; the response flows back the same path in reverse.

    HTTP fundamentals: request and response

    HTTP (HyperText Transfer Protocol) is the rules both sides follow. Every request names a method (what kind of action) and a URL (which resource); every response carries a status code and, usually, a body.

    HTTP methods and status codes

    • GET — retrieve data, safe to repeat, no side effects.
    • POST — create something new.
    • PUT/PATCH — update an existing resource.
    • DELETE — remove a resource.
    • 2xx — success (200 OK, 201 Created).
    • 4xx — the client's request was the problem (400 Bad Request, 404 Not Found).
    • 5xx — the server failed while processing an otherwise valid request (500 Internal Server Error).

    Headers and JSON

    Headers carry metadata about a request or response — content type, authentication tokens, caching rules — separately from the actual body. Most modern APIs exchange data as JSON, the same lightweight, human-readable format you may already know from reading or writing files. 

    {
  "id": 42,
  "name": "Alex",
  "isActive": true
}

    REST principles and API endpoints

    REST is a set of conventions for designing APIs around resources, identified by URLs, manipulated with standard HTTP methods. An endpoint is one specific URL path an API exposes: 

    GET    /users        # list all users
GET    /users/42     # get one specific user
POST   /users        # create a new user
PUT    /users/42     # update user 42
DELETE /users/42     # delete user 42

    Query parameters and request bodies

    A GET request typically passes extra information as query parameters in the URL (/users?role=admin&page=2). A POST/PUT request typically carries its data in the request body, usually as JSON, since URLs aren't a good place to send a lot of structured data.

    API error handling

    A well-designed API returns the right status code for what actually went wrong — 400 for a malformed request, 404 for a resource that doesn't exist, 401/403 for authentication and permission problems (Module 9 covers these in depth), and a clear error message in the body explaining what to fix. 

    {
  "error": "Missing required field: email"
}
    Common mistakes

    Common mistakes

    • Using GET for a request that changes data — GET should be safe to repeat with no side effects.
    • Returning 200 OK even when an error occurred, with the actual problem only described somewhere in the body text.
    • Putting sensitive data in query parameters, which often end up logged in server access logs and browser history.
    Best practices

    Best practices

    • Match the HTTP method to the actual action: GET to read, POST to create, PUT/PATCH to update, DELETE to remove.
    • Return the status code that accurately describes what happened, not just 200 for everything.
    • Design endpoints around resources ("/users/42") rather than actions ("/getUserById?id=42").
    Summary

    Key takeaways

    • The client always initiates; the server processes and responds — the request/response cycle.
    • HTTP methods signal intent (GET reads, POST creates, PUT/PATCH updates, DELETE removes); status codes signal outcome (2xx/4xx/5xx).
    • REST designs APIs around resources and URLs, manipulated with standard HTTP methods, usually exchanging JSON.
    • 4xx means the client's request was the problem; 5xx means the server failed on an otherwise valid request.
