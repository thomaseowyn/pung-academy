Backend Development

    Introduction

    What you'll learn in this module

    Modules 6 and 7 gave you SQL and HTTP separately. This module wires them together into an actual running backend — routing requests, separating business logic from that routing, talking to a database, validating input, and structuring a project so it stays sane as it grows.

    Learning material

    What a backend does

    A backend is the program that receives requests (Module 7), runs the logic those requests trigger, talks to a database (Module 6) when needed, and sends back a response. Everything from here builds one working backend out of pieces you already know.

    Frontend
    (browser)     → Routing → Business logic
    (service)     → Database

    A request flows through each layer in order; the response flows back the same way.

    Routing

    Routing matches an incoming request's method and URL to the specific function that should handle it — the first stop for every request, before any real logic runs. 

    from fastapi import FastAPI

app = FastAPI()

@app.get("/tasks")
def list_tasks():
    ...

@app.post("/tasks")
def create_task():
    ...

    Controllers/services and business logic

    Route handlers should stay thin — matching Module 5's Single Responsibility Principle, the actual rules (what makes a task valid, what happens when one is completed) belong in a separate function, often called a service. This keeps the logic testable and reusable on its own, without needing a fake HTTP request to call it. 

    def create_task_service(title: str) -> dict:
    # business logic lives here, independent of HTTP
    return {"title": title, "is_done": False}

@app.post("/tasks")
def create_task(title: str):
    return create_task_service(title)

    Database integration

    Somewhere behind the service layer, a function actually runs the SQL from Module 6 — inserting, reading, updating, or deleting rows — and hands the results back up to the service that called it.

    CRUD APIs and validation

    A typical resource gets exactly the four CRUD operations from Module 6, each behind a REST endpoint from Module 7: 

    GET    /tasks       # read (list)
POST   /tasks       # create
PUT    /tasks/{id}  # update
DELETE /tasks/{id}  # delete

    Before any of that logic runs, validation checks the request actually contains what it needs — a missing or malformed field should be rejected immediately, with a clear error (Module 7), rather than crashing deeper in the program.

    Dependency management and environment variables

    A backend depends on external packages (Module 1's uv-style dependency management applies here too) and on configuration that changes between environments — database URLs, API keys — kept in environment variables and a .env file, never hard-coded (Module 2's .gitignore habit applies directly).

    Structuring a backend project

    project/
  main.py           # app setup, routing
  services/
    tasks.py        # business logic
  models/
    task.py         # data shape
  database.py       # database connection
  .env              # secrets (never committed)
  .gitignore

    This is Module 3's "modular programming" and Module 5's "separation of concerns," applied to an entire project's folder structure instead of just one file.

    Common mistakes

    Common mistakes

    • Putting database queries and business rules directly inside route handlers, making them impossible to test without spinning up a full HTTP server.
    • Trusting request data without validating it first, letting malformed input reach the database layer.
    • Hard-coding a database URL or API key directly in source code instead of reading it from an environment variable.
    Best practices

    Best practices

    • Keep route handlers thin — parse the request, call a service function, return its result.
    • Validate input at the boundary, before it reaches business logic or the database.
    • Read configuration from environment variables, with a .env file for local development that's always in .gitignore.
    Summary

    Key takeaways

    • A backend routes a request, runs business logic in a separate layer, talks to a database, and returns a response.
    • Separating routing from business logic keeps logic testable and reusable, per Module 5's SRP.
    • CRUD operations map naturally onto REST endpoints and HTTP methods.
    • Configuration and secrets belong in environment variables, never hard-coded or committed.
