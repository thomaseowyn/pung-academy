Module 9

Authentication & Sessions

    Introduction

    What you'll learn in this module

    Your Module 8 backend can now serve requests — but it has no idea who's asking. This module covers proving who a user is (authentication), deciding what they're allowed to do (authorization), storing passwords safely, and keeping a user recognised across multiple requests with sessions and tokens.

    Learning material

    Authentication vs. authorization

    Authentication answers "who are you?" — usually a username/password check, or a valid token. Authorization answers a separate question, asked afterward: "now that I know who you are, are you allowed to do this?" A logged-in user can be authenticated and still be denied a specific action.

    Password security and hashing

    A password should never be stored as plain text — if the database ever leaks, every stored password leaks with it. Instead, a hash — a one-way transformation — is stored. Logging in re-hashes the entered password and compares hashes; the original password is never saved anywhere. 

    import bcrypt

hashed = bcrypt.hashpw(b"my-password", bcrypt.gensalt())
# store `hashed`, never the original password

bcrypt.checkpw(b"my-password", hashed)  # True — used to verify login

    Sessions

    HTTP is stateless — the server doesn't remember you between requests by default. A session fixes this server-side: after login, the server stores session data and gives the client a small reference (usually a cookie) to send back on every future request.

    JWT and access tokens

    A JWT (JSON Web Token) takes a different approach: instead of the server storing session data, the token itself carries signed claims (like a user id) that the server can verify without a lookup. This is common for APIs that don't want to maintain shared session storage.

    Client submits
    credentials     → Server verifies
    hashed password     → Server issues
    session/token     → Client resends it
    on every request

    After this handshake, the server (or the token itself) recognises the same user on every later request.

    Roles and permissions

    Once a user is authenticated, roles (like "admin" or "member") drive authorization decisions — which endpoints or actions a given user is allowed to reach. 

    def require_admin(current_user):
    if current_user.role != "admin":
        raise PermissionError("Admins only")
    Careful

    Checking a role on the frontend only (hiding a button) is not authorization — it's decoration. The backend must enforce the check itself, since any request can be sent directly, bypassing the frontend entirely.

    Common mistakes

    Common mistakes

    • Storing passwords in plain text, or with a weak/reversible encoding instead of a proper one-way hash.
    • Checking permissions only in the frontend UI, with no matching check on the backend.
    • Treating "authenticated" and "authorized to do this specific thing" as the same check.
    Best practices

    Best practices

    • Always hash passwords with a proper algorithm designed for it (like bcrypt), never a general-purpose hash used alone.
    • Enforce every authorization check on the backend — the frontend is a convenience, not a security boundary.
    • Keep authentication (who) and authorization (what they can do) as two explicit, separate checks in your code.
    Summary

    Key takeaways

    • Authentication confirms identity; authorization decides what that identity is allowed to do.
    • Passwords are stored as one-way hashes, never as plain text.
    • Sessions and JWTs both solve the same problem — recognising a user across HTTP's stateless requests — in different ways.
    • Authorization must be enforced on the backend, regardless of what the frontend shows or hides.
