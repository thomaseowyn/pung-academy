Module 13

Deployment & DevOps Basics

    Introduction

    What you'll learn in this module

    A tested (Module 11), secure (Module 10) backend still has to reach real users. This module covers the gap between "runs on my machine" and "runs reliably in production" — environments, containers, and the CI/CD pipeline that automates getting changes there safely.

    Learning material

    Development vs. production

    Development is where code is written and tested, often with fake data and relaxed settings. Production is the live system real users depend on. Keeping them close in behaviour (same dependencies, similar configuration) is what makes "it worked in development" a meaningful signal instead of a false promise.

    Build and deployment, servers, and basic Linux

    A build turns source code into something runnable. Deployment gets that build onto a server — a machine (often running Linux) that stays on and reachable, running your application continuously.

    Docker: containers vs. virtual machines

    A container packages an application and its dependencies together, sharing the host machine's OS kernel — lightweight and fast to start. A virtual machine virtualizes an entire separate operating system — heavier, but more isolated. Docker is the standard tool for building and running containers. 

    # Dockerfile
FROM python:3.12-slim
COPY . /app
WORKDIR /app
RUN pip install -r requirements.txt
CMD ["uvicorn", "main:app", "--host", "0.0.0.0"]

    CI/CD and GitHub Actions concepts

    CI/CD (Continuous Integration/Continuous Deployment) automates what happens after code is pushed: build it, run the test suite (Module 11) automatically, and only deploy if everything passes. GitHub Actions is one common tool for defining this pipeline directly alongside the code it tests.

    Code pushed → Build → Tests run → Deploy

    A failing test at any step blocks the pipeline — broken code never reaches production automatically.

    Logging, monitoring, and basic cloud concepts

    Once deployed, logging (Module 11) and monitoring are what tell you the system is actually healthy — or alert you the moment it isn't. Cloud providers (AWS, Google Cloud, Azure) rent out servers, storage, and managed services on demand, instead of a team buying and maintaining physical hardware themselves.

    Common mistakes

    Common mistakes

    • Deploying manually and inconsistently instead of through an automated, repeatable pipeline.
    • Letting development and production configurations drift far apart, so "it worked locally" stops meaning anything.
    • Deploying with no logging or monitoring in place, so a production failure is only noticed when a user reports it.
    Best practices

    Best practices

    • Automate deployment through CI/CD rather than manual steps — consistency matters more than speed here.
    • Never let a failing test block be bypassed just to ship faster — that's exactly what the pipeline exists to prevent.
    • Set up basic logging and monitoring before you need them, not after a production incident.
    Summary

    Key takeaways

    • Development is for building and testing; production is the live system users depend on.
    • Containers share the host OS kernel and are lightweight; VMs virtualize a full separate OS.
    • CI/CD automates build → test → deploy, blocking a broken build or failing test from reaching production.
    • Logging and monitoring are what make a production issue visible before a user has to report it.
