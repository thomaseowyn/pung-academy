Software Engineering Fundamentals

    Introduction

    What you'll learn in this module

    By the end of this module you'll be able to explain what software engineering actually is, walk through the phases every software project moves through (the SDLC), tell Waterfall and Agile apart and know when each fits, describe how a Scrum team organises its work, and turn a vague idea into concrete functional and non-functional requirements.

    Learning material

    What software engineering actually is

    Anyone can write code that works once, on their own machine, for their own use. Software engineering is the discipline of building software that keeps working — reliably, for other people, for years, as requirements change and the team around it changes too. The difference isn't the programming language or how many lines of code you write; it's process, collaboration, testing, and design discipline layered on top of the code itself.

    Real-world example

    A weekend hobby script that scrapes a website for you is code. The same idea, rebuilt so it handles the website changing its layout, alerts someone when it breaks, has automated tests, and can be safely modified by a teammate who has never seen it before — that's software engineering.

    The Software Development Life Cycle (SDLC)

    Every software project, regardless of methodology, moves through the same broad phases — the Software Development Life Cycle:

    Requirements → Design → Implementation → Testing → Deployment → Maintenance

    Maintenance usually lasts far longer than every other phase combined.

    What differs between methodologies isn't these phases — it's how many times you move through them, and how big each pass is.

    Waterfall vs. Agile

    Waterfall moves through the SDLC once, in strict sequence: all requirements are gathered up front, then design, then implementation, and so on. It works well when requirements are genuinely stable and well understood in advance — construction and safety-critical systems often use it.

    Agile instead moves through small versions of the whole cycle repeatedly, in short iterations, re-planning based on real feedback each time. It fits the far more common situation where nobody has perfect information up front and requirements are expected to evolve.

    Tip

    Neither approach is universally "better" — Waterfall trades flexibility for predictability; Agile trades some predictability for the ability to adapt. Most real teams today lean Agile, because most real requirements do change.

    Scrum fundamentals

    Scrum is the most common way teams actually practise Agile. Work is planned and delivered in fixed-length iterations called sprints (commonly 1-2 weeks), with a small set of recurring ceremonies:

    • Sprint planning — deciding what work fits in the upcoming sprint.
    • Daily stand-up — a short daily sync on progress and blockers.
    • Sprint review — demoing what was actually finished.
    • Retrospective — reflecting on what to improve next sprint.

    Gathering requirements: functional vs. non-functional

    Before any design happens, a team has to know what to build. Functional requirements describe what the system does — "users can reset their password," "admins can export data as CSV." Non-functional requirements describe how well it does it — performance, security, reliability, usability. A system can satisfy every functional requirement and still be unusable if it takes ten seconds to load a page.

    Real-world example

    "Users can search for a product" is functional. "Search results must return within 300ms for 95% of requests" is non-functional — it says nothing new about what search does, only how well it has to perform.

    A real-world development workflow

    Put together, a real feature's life looks roughly like this: a product owner writes a requirement, the team breaks it into smaller tasks during sprint planning, an engineer implements it on a branch (Module 2), it's reviewed and merged, tested, and released — then the cycle repeats for the next sprint, informed by what was learned from the last one.

    Common mistakes

    Common mistakes

    • Treating "we'll figure out requirements as we go" as an excuse to skip requirements gathering entirely, rather than as a reason to use shorter iterations.
    • Confusing a functional requirement with a non-functional one, and only ever writing down the former — performance and security requirements get discovered painfully late.
    • Assuming Agile means "no planning" — Scrum still plans deliberately, just in smaller increments.
    Best practices

    Best practices

    • Write requirements down, even briefly — a shared, written understanding beats everyone assuming they agree.
    • Separate "what it does" from "how well it does it" explicitly when gathering requirements, so non-functional needs don't get silently dropped.
    • Pick a methodology to fit the project's actual uncertainty, not out of habit — a well-understood, stable project can genuinely suit Waterfall.
    Summary

    Key takeaways

    • Software engineering is process and discipline layered on top of code, aimed at keeping software reliable over time.
    • Every project moves through the same SDLC phases; methodologies differ in how many times and how big each pass through them is.
    • Waterfall suits stable, well-understood requirements; Agile/Scrum suits requirements expected to change.
    • Functional requirements describe what a system does; non-functional requirements describe how well it does it.
