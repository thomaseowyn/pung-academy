Data Structures & Algorithms

    Introduction

    What you'll learn in this module

    By the end of this module you'll recognise the handful of data structures behind almost every program (arrays, stacks, queues, hash tables, linked lists, trees), understand searching and sorting at a conceptual level, and be able to use Big-O notation to reason about how a choice of structure or algorithm scales as data grows.

    Learning material

    Why data structures matter

    The same data can be organised many different ways, and the organisation you choose directly determines how fast (or slow) common operations are. Picking the right structure is often the single biggest performance decision in a program — far bigger than micro-optimising the code around it.

    Arrays/lists, stacks, and queues

    • Array/list — items in order, accessed by position (index). Python's list is this.
    • Stack — Last-In-First-Out (LIFO): the most recently added item comes out first. Undo history is a stack.
    • Queue — First-In-First-Out (FIFO): the oldest item comes out first. A print queue or a line of people is a queue.
    # A list used as a stack
stack = []
stack.append("a")   # push
stack.append("b")
stack.pop()          # "b" — the most recent one comes off first

# A list used as a queue (using collections.deque for efficiency)
from collections import deque
queue = deque()
queue.append("a")    # enqueue
queue.append("b")
queue.popleft()       # "a" — the oldest one comes off first

    Hash tables / dictionaries

    A hash table (Python's dict) computes roughly where a value lives directly from its key, giving average constant-time lookup, insertion, and deletion — dramatically faster than scanning a list item by item to find a match.

    Linked lists and trees

    A linked list stores items as a chain of nodes, each pointing to the next — inserting in the middle is cheap, but reaching item 500 means walking through the 499 before it. A tree organises items hierarchically (a parent with children, e.g. a file system's folder structure), which is what makes searching a sorted tree much faster than scanning a flat list.

    Searching and sorting

    Linear search checks every item one by one until it finds a match. Binary search, on a sorted list, repeatedly cuts the remaining search space in half — far fewer comparisons, but it only works because the data is sorted first. 

    def linear_search(items, target):
    for index, value in enumerate(items):
        if value == target:
            return index
    return -1

    Big-O notation

    Big-O notation describes how an algorithm's running time (or memory use) grows as the input size n grows — not the exact time, but the shape of its growth.

    O(1) — constant, doesn't grow with n O(log n) — grows very slowly O(n) — grows in direct proportion to n O(n log n) — typical of efficient sorting O(n²) — grows fastest, gets slow quickly

    Time vs. space complexity

    Big-O can describe either time (how many operations) or space (how much extra memory) an algorithm needs. The two often trade off against each other — a hash table trades extra memory for faster lookups than a plain list would give you.

    Choosing the right data structure

    The practical question is almost always: what operation happens most often, and how does each structure perform at that specific operation? Frequent lookups by key → a dictionary. Frequent "most recent item first" → a stack. Frequent "process in arrival order" → a queue.

    Common mistakes

    Common mistakes

    • Using a list and scanning it (O(n)) for membership checks that happen constantly, when a set would give near-instant (O(1)) lookups.
    • Assuming "it works fine with my 10 test rows" says anything about how it performs with 10 million rows.
    • Optimising the wrong part of a program before measuring where the actual time is being spent.
    Best practices

    Best practices

    • Reach for a dict/set the moment "does this exist?" or "look this up by key" happens frequently.
    • Know the rough Big-O of the structures and functions you use most, even without formally proving them.
    • Only optimise after identifying an actual bottleneck — premature optimisation often adds complexity without a measurable benefit.
    Summary

    Key takeaways

    • Stacks are LIFO, queues are FIFO — pick based on which end needs to come out first.
    • Hash tables (dicts/sets) give average O(1) lookup by key — the go-to structure for frequent membership checks.
    • Big-O describes how performance scales with input size, not exact speed — O(1) < O(log n) < O(n) < O(n log n) < O(n²).
    • Choose a structure based on which operation happens most often in your actual use case.
