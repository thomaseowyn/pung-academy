Git & Version Control

    Introduction

    What you'll learn in this module

    By the end of this module you'll understand why version control is non-negotiable on any real project, know the difference between Git and GitHub, be comfortable with the core add/commit/push workflow, and understand branching, pull requests, and merge conflicts well enough to work on a shared codebase with a team.

    Learning material

    Why version control matters

    Without version control, "keeping track of changes" usually means files named project_final_v2_REAL.py. Git replaces that with a real history: every saved snapshot is recorded, nothing is ever silently lost, and multiple people can work on the same project at once without overwriting each other's work.

    Git vs. GitHub

    Git is the version-control tool itself — it runs entirely on your own machine and needs no internet connection to track history. GitHub is a separate hosting service built around Git repositories, adding collaboration features on top: pull requests, code review, issue tracking. GitLab and Bitbucket do the same job as GitHub — Git itself doesn't require any of them.

    Repository, commit, branch, merge

    • Repository (repo) — a project, plus its entire tracked history.
    • Commit — a saved snapshot of the project at one point, with a message describing what changed.
    • Branch — an independent line of development, so you can work on something without touching the main, stable version.
    • Merge — combining the changes from one branch into another.

    Working tree and staging area

    A change doesn't become a commit in one step — it passes through three places:

    Working directory
    (your edited files)     → Staging area
    (git add)     → Repository
    (git commit)     → Remote
    (git push)

    git add moves changes to staging; git commit saves them to local history; git push shares that history remotely.

    The staging area exists so you can choose exactly which changed files go into the next commit, rather than being forced to commit everything you've touched at once.

    Essential Git commands

    git init                        # start tracking a folder
git status                      # see what's changed
git add file.py                 # stage one file
git add .                       # stage everything changed
git commit -m "Add login form"  # save a snapshot with a message
git log                         # view commit history
git push                        # send commits to the remote
git pull                        # fetch and merge remote changes

    Branching strategies

    Real teams almost never commit directly to the main branch. Instead, each new piece of work gets its own branch (often named like feature/login-form or fix/broken-link), keeping main always in a working, deployable state. 

    git checkout -b feature/login-form   # create and switch to a new branch
# ... make changes, commit them ...
git push -u origin feature/login-form

    Pull requests and merge conflicts

    A pull request (PR) proposes merging one branch into another and gives teammates a chance to review the change before it lands. If two people changed the exact same lines of the same file differently, Git can't guess which version is correct — it marks the file as conflicted and a person has to resolve it by hand, choosing or combining the changes.

    Careful

    A merge conflict is not an error you did something wrong — it's Git correctly refusing to guess. Read both versions carefully before resolving; picking the wrong side silently deletes real work.

    Commit best practices and .gitignore

    A good commit message describes why, not just what ("Fix session timeout on password reset" beats "fix bug"). A .gitignore file lists patterns Git should never track — dependency folders, build output, and, critically, anything holding a secret.

    Common mistakes

    Common mistakes

    • Committing a .env file or an API key before adding it to .gitignore — once it's in history, treat it as leaked and rotate it.
    • Making one giant commit at the end of a day's work instead of small, focused commits — hard to review, hard to undo just one part.
    • Panicking during a merge conflict and discarding one side entirely without reading it, instead of carefully reconciling both changes.
    Best practices

    Best practices

    • Commit often, in small, logically complete chunks — each commit should represent one coherent change.
    • Write commit messages in the imperative mood ("Add," "Fix," "Remove") describing intent, not just a diff summary.
    • Create a .gitignore before your very first commit, not after.
    • Keep main always deployable — do new work on branches, merged in through reviewed pull requests.
    Summary

    Key takeaways

    • Git tracks history locally; GitHub (or similar) hosts repositories and adds collaboration features on top.
    • A change moves working directory → staging (git add) → repository (git commit) → remote (git push).
    • Branches isolate work in progress; pull requests propose merging it back, with review, into a shared branch.
    • Merge conflicts happen when the same lines change on both sides — Git asks a human to resolve them, rather than guessing.
