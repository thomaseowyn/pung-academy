Module 10

Web Security Fundamentals

    Introduction

    What you'll learn in this module

    Module 9 covered proving who someone is. This module covers defending against people actively trying to abuse your backend: SQL injection, cross-site scripting, cross-site request forgery, and the basic hygiene — secrets management, HTTPS — that closes off the most common attacks entirely.

    Learning material

    Input validation

    Almost every attack in this module starts the same way: untrusted input (from a user, a form, another API) is trusted and used without checking it first. Validating input at the boundary — the moment it enters your system — is the single habit that prevents the most damage.

    SQL injection

    When user input is pasted directly into a SQL query string, an attacker can craft input that changes what the query actually does. 

    # Vulnerable: user input becomes part of the query itself
query = f"SELECT * FROM users WHERE username = '{username}'"
# If username is:  ' OR '1'='1
# the query becomes: ...WHERE username = '' OR '1'='1'  — always true

# Safe: input passed as a separate, escaped parameter
cursor.execute("SELECT * FROM users WHERE username = ?", (username,))

    A parameterized query sends the SQL structure and the data separately — the database driver handles escaping correctly, so user input can never be interpreted as part of the query's structure, no matter what's typed.

    XSS and CSRF

    • Cross-Site Scripting (XSS) — untrusted input (a comment, a username) gets rendered back into a page without escaping, so a malicious <script> tag runs in other users' browsers. Prevented by escaping output, and modern frontend frameworks doing this by default.
    • Cross-Site Request Forgery (CSRF) — a malicious site tricks a logged-in user's browser into sending a request to your site the user never intended. Prevented with CSRF tokens that verify the request genuinely came from your own frontend.

    Secrets and environment variables

    API keys, database passwords, and signing secrets belong in environment variables (Module 8), never in source code. A secret that ever touches git history — even if removed in a later commit — should be treated as leaked and rotated immediately (Module 2).

    HTTPS

    HTTPS encrypts traffic between client and server, so anyone intercepting the connection (a shared network, an ISP, an attacker on the same WiFi) sees only scrambled bytes — not passwords, tokens, or personal data in plain text.

    Common security mistakes

    Most real security incidents aren't exotic — they're one of the basics in this module skipped under time pressure: unvalidated input, a leaked key, a missing authorization check (Module 9) that nobody tested for.

    Common mistakes

    Common mistakes

    • Building SQL queries with string concatenation or f-strings instead of parameterized queries.
    • Rendering user-provided text into a page without escaping it, opening the door to XSS.
    • Assuming "it's just an internal tool" means security doesn't matter — internal tools get breached too.
    Best practices

    Best practices

    • Always use parameterized queries — never build SQL by concatenating user input into a string.
    • Escape output rendered from untrusted input, and use CSRF tokens on state-changing requests.
    • Treat every secret as sensitive by default: environment variables, never source code, never committed.
    • Serve everything over HTTPS — there's no good reason for a modern site not to.
    Summary

    Key takeaways

    • SQL injection and XSS both stem from trusting unescaped input — parameterized queries and output escaping close them off.
    • CSRF tricks a logged-in user's own browser into sending an unintended request; CSRF tokens verify requests are genuine.
    • Secrets belong in environment variables, never in code or git history.
    • HTTPS encrypts data in transit — a baseline, not an optional extra.
