Module 3

Programming for Software Engineers

    Introduction

    What you'll learn in this module

    You already know Python syntax. This module is about writing it differently — breaking work into focused, reusable pieces, understanding scope, hiding complexity behind clean interfaces, handling errors on purpose, and documenting intent with type hints — the habits that separate a script from a program a team can maintain.

    Learning material

    Procedural vs. modular programming

    A procedural script runs top to bottom, one long sequence of steps, often with logic repeated wherever it's needed. Modular programming breaks the same work into separate functions and modules, each with one clear job, that can be reused, tested, and understood independently of everything else. 

    # Procedural: the same validation logic copy-pasted twice
if "@" in email_a and "." in email_a:
    ...
if "@" in email_b and "." in email_b:
    ...

# Modular: the rule lives in one place
def is_valid_email(text: str) -> bool:
    return "@" in text and "." in text

if is_valid_email(email_a):
    ...
if is_valid_email(email_b):
    ...

    Variables, functions, and modules

    A module is just a file of related functions and variables that other files can import. As a program grows, grouping related functions into their own module (e.g. validation.py, database.py) keeps any one file from becoming an unmanageable dumping ground.

    Scope and state

    A variable's scope is where in the program it can be seen and used. A variable defined inside a function is local — it disappears once the function returns. A variable defined outside any function is global — visible everywhere, which sounds convenient but makes it hard to know what part of a large program might have changed it.

    Careful

    Relying on global variables for shared state is one of the fastest ways to make a program hard to reason about — any function, anywhere, might silently change it. Prefer passing values explicitly as function parameters and return values.

    Abstraction and reusability

    Abstraction means hiding how something works behind a simple interface — you call sorted(my_list) without knowing or caring which sorting algorithm Python uses internally. Writing your own functions this way (a clear name and signature, hidden internals) is what makes them genuinely reusable — a caller only needs to know what a function does, never how.

    Error handling

    Production code has to expect things going wrong: a missing dictionary key, a file that doesn't exist, a network call that times out. try/except lets a program catch a specific, anticipated failure and decide what to do instead of crashing outright. 

    try:
    age = int(user_input)
except ValueError:
    print("Please enter a whole number.")

    Type hints

    Type hints document what a function expects and returns, directly in its signature. Python doesn't enforce them at runtime, but editors and linters use them to catch a whole class of mistakes — passing a string where a number was expected — before the code ever runs. 

    def total_price(quantity: int, unit_price: float) -> float:
    return quantity * unit_price

    Writing maintainable programs, structured from the start

    Even a small application benefits from separating concerns into files: input/output in one place, business logic in another, data access in a third. This is the same idea Module 5 explores in depth as "separation of concerns" — here, it just means: don't let one 200-line function do everything.

    Common mistakes

    Common mistakes

    • Copy-pasting a block of logic into a second place instead of extracting it into a function (see Module 5's "DRY" for why this matters).
    • Catching every possible exception with a bare except:, which also silently swallows real bugs you actually needed to see.
    • Writing a function whose name doesn't match what it actually does, forcing anyone reading a call site to go read its implementation to understand it.
    Best practices

    Best practices

    • Give every function one clear job and a name that describes exactly that job.
    • Catch specific exceptions (ValueError, KeyError) rather than a bare except:, so unexpected bugs still surface.
    • Add type hints to function signatures, especially on anything another engineer will call.
    • Prefer passing data explicitly through parameters and return values over relying on shared global state.
    Summary

    Key takeaways

    • Modular code breaks work into focused, independently reusable pieces instead of one long procedural script.
    • Scope determines where a variable is visible; prefer local variables and explicit parameters over global state.
    • Abstraction hides implementation behind a stable interface, which is what makes code genuinely reusable.
    • Handle errors you can anticipate with specific try/except blocks; document intent with type hints.
