Module 5

Software Design Principles

    Introduction

    What you'll learn in this module

    This module covers the small set of principles experienced engineers reach for constantly — separation of concerns, DRY, KISS, YAGNI, Single Responsibility, coupling and cohesion — not as abstract rules to memorise, but as answers to "why does this codebase feel painful to change?"

    Learning material

    Separation of concerns

    A well-designed program splits distinct responsibilities — reading input, applying business rules, storing data — into separate parts, each concerned with exactly one of them. When concerns are tangled together, a small change to one (say, how data is stored) risks breaking something completely unrelated (say, how input is validated).

    DRY, KISS, and YAGNI

    • DRY (Don't Repeat Yourself) — every piece of knowledge should live in exactly one place. Copy-pasted logic means every future fix has to be applied everywhere it was copied, and it's easy to miss a spot.
    • KISS (Keep It Simple) — prefer the simplest solution that correctly solves the actual problem. Cleverness that isn't needed is a liability, not a virtue.
    • YAGNI (You Aren't Gonna Need It) — don't build flexibility or features for requirements that don't exist yet. Speculative complexity costs real time today for a maybe that may never arrive.
    # Violates KISS: needlessly clever for what it does
def is_even(n):
    return not bool(n & 1)

# Follows KISS: says exactly what it means
def is_even(n):
    return n % 2 == 0

    Single Responsibility Principle

    A class or function should have exactly one reason to change. A UserManager class that validates input, saves to a database, and sends confirmation emails has at least three reasons to change — a new validation rule, a new database, a new email provider — and any of them forces you to touch the same class.

    Dependency inversion

    Instead of a high-level piece of code depending directly on a specific low-level detail (a specific database library, a specific email service), both should depend on a shared, stable interface. This is what lets you swap the concrete implementation later (switch databases, switch email providers) without rewriting the code that uses it.

    Coupling and cohesion

    Coupling is how much one module depends on another module's internal details — low coupling means modules interact only through a small, stable interface, so a change inside one is unlikely to break the other. Cohesion is how closely related the responsibilities inside a single module are — high cohesion means everything in that module genuinely belongs together. Good design aims for low coupling, high cohesion.

    Composition

    Rather than building one large class that tries to do everything, composition builds a larger behaviour out of smaller, focused pieces plugged together — a Car that has an Engine, rather than a Car that reimplements engine logic itself. This tends to produce more flexible, more testable designs than deep inheritance hierarchies.

    Designing reusable components

    Putting these principles together: a reusable component does one job (SRP), doesn't repeat logic that exists elsewhere (DRY), is no more complex than the job requires (KISS), only handles requirements that actually exist today (YAGNI), and exposes a small, stable interface that hides its internals (low coupling, abstraction from Module 3).

    Common mistakes

    Common mistakes

    • Adding configuration options, plugin systems, or extra flexibility for a need that doesn't exist yet ("we might need it later") — a YAGNI violation that costs real complexity today.
    • Treating "it's all related to users" as license to put validation, storage, and email-sending in one class — SRP is about reasons to change, not vague topical relatedness.
    • Confusing DRY with "never write similar-looking code twice" — two pieces of code that happen to look similar but represent different business rules are not a DRY violation.
    Best practices

    Best practices

    • Before adding flexibility, ask: is this solving a requirement that exists right now, or one you're guessing about?
    • When a class is hard to name in one sentence, it's probably doing more than one job.
    • Depend on interfaces/abstractions for anything likely to change (databases, external services), not concrete specifics.
    Summary

    Key takeaways

    • DRY, KISS, and YAGNI each guard against a different kind of unnecessary cost: duplication, complexity, and speculative work.
    • Single Responsibility Principle: one class, one reason to change.
    • Aim for low coupling (modules don't depend on each other's internals) and high cohesion (a module's own responsibilities belong together).
    • Composition builds complex behaviour from small, focused, reusable pieces.
