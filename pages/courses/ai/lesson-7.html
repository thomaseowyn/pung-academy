Deploying the AI Backend (FastAPI)

    Learning material

    Chapter 6 left you with a genuinely capable agent — grounded, structured, remembered, self-correcting. This final chapter answers the one remaining question: how does anyone outside your terminal actually use it?

    FastAPI fundamentals

    Everything so far has run as a script. A real product needs a web server a frontend can talk to. FastAPI is the standard choice for this in Python: fast, built on the same async foundations from Chapter 1, and designed around type hints and dependency injection rather than manual boilerplate. 

    from fastapi import FastAPI

app = FastAPI()

@app.get("/health")
async def health():
    return {"status": "ok"}

# uv run fastapi dev main.py

    A health check proves the server runs. The next step is an endpoint that actually does something — and does it safely.

    AI endpoints with Pydantic validation

    A request body is just another place Pydantic validates data — define the shape of what the frontend sends, and FastAPI rejects anything malformed before your endpoint code even runs. 

    from pydantic import BaseModel

class ChatRequest(BaseModel):
    message: str
    conversation_id: str

class ChatResponse(BaseModel):
    reply: str

@app.post("/chat", response_model=ChatResponse)
async def chat(request: ChatRequest):
    reply = await fetch_completion(request.message)   # Chapter 1's async call
    return ChatResponse(reply=reply)

    The response_model works the same way in reverse — FastAPI validates what your endpoint returns, so a bug that produces the wrong shape of response is caught immediately instead of silently reaching the frontend.

    That endpoint works, but it makes the browser wait in silence for the entire reply. Chapter 2 solved this exact problem for a server-side script — the same idea now needs to reach the browser itself.

    Server-Sent Events (SSE)

    A normal response only reaches the browser once the whole body is ready. To get the same live "typing" effect you streamed server-side in Chapter 2, the endpoint itself needs to stream — keeping the connection open and pushing each chunk to the client the moment it's generated. 

    from fastapi.responses import StreamingResponse

@app.post("/chat/stream")
async def chat_stream(request: ChatRequest):
    async def token_generator():
        stream = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": request.message}],
            stream=True,
        )
        for chunk in stream:
            delta = chunk.choices[0].delta.content
            if delta:
                yield f"data: {delta}\n\n"

    return StreamingResponse(token_generator(), media_type="text/event-stream")

    A streaming endpoint is only half a product without something on the other end actually consuming it. That's the last piece.

    Full-stack integration

    The final piece is a frontend simple enough to prove the whole chain works: a page that sends a message to /chat (or reads the /chat/stream event source) and displays the reply. 

    <script>
async function sendMessage() {
  const response = await fetch("/chat", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ message: input.value, conversation_id: "demo" }),
  });
  const data = await response.json();
  output.textContent = data.reply;
}
</script>
    Note

    This is the same request/response shape you've used from Python throughout the course — a browser's fetch is just another HTTP client talking to your FastAPI endpoint, the same way httpx talked to OpenAI's API back in Chapter 1.

    Common mistakes

    Common mistakes

    • Putting business logic directly in a route handler instead of a separate, testable function underneath it.
    • Skipping response_model validation, so a bug that changes the response shape only gets caught by the frontend failing to parse it.
    • Building a chat endpoint without streaming, forcing the frontend to wait for the entire reply before showing anything.
    Best practices

    Best practices

    • Validate both requests and responses with Pydantic models, not just one side.
    • Stream any AI-generated reply a user is actively waiting on, using StreamingResponse and SSE.
    • Keep the same async patterns from Chapter 1 all the way through the backend — a synchronous call anywhere in the chain can block the whole event loop.
    Summary

    Key takeaways

    • FastAPI routes requests to Python functions, validating both requests and responses with Pydantic.
    • StreamingResponse and Server-Sent Events bring the same chunk-by-chunk delivery from Chapter 2's API calls to a real frontend.
    • A browser's fetch is just another HTTP client talking to your API, the same way httpx talked to the LLM provider.
    • Every chapter in this course is one stage a real chat request actually passes through, end to end.
    Practical

    Practical things you can apply right now

    • Stand up a minimal FastAPI app with one /health route and run it locally with fastapi dev.
    • Add a /chat POST endpoint that takes a Pydantic request body and calls an LLM using your Chapter 1/2 code.
    • Upgrade that endpoint to a /chat/stream route using StreamingResponse and confirm chunks arrive incrementally, not all at once.
    • Build one plain HTML page with a text input and a button that calls your endpoint and displays the reply — your first real full-stack AI feature.
