Chapter 3

Advanced Prompt Engineering & Architecture

    Learning material

    Architecture of a production prompt

    Chapter 2 introduced system/user/assistant roles as an API detail. In production, the system (or, on some providers, a separate "developer") role carries the actual architecture of your application: rules, tone, output format, and constraints, kept deliberately separate from whatever the user types.

    A subtler issue shows up as prompts get longer: models don't attend equally to every part of a long context. This is the "lost in the middle" phenomenon — instructions and facts near the very start or very end of a long prompt tend to be followed far more reliably than ones buried in the middle of a long block of injected text.

    Start of prompt
    (strong attention)     Middle of prompt
    (weakest attention)     End of prompt
    (strong attention)

    Put your most important rules at the start or end — never rely on the model noticing something buried in the middle.

    Careful

    If you're stuffing retrieved documents (Chapter 5) or long conversation history into a prompt, put your most important rules at the very start or the very end — never rely on the model noticing something you buried in the middle of a large block of context.

    Knowing where the model pays the most attention is one half of the problem. The other half is making sure it can actually tell your rules apart from everything else you've stuffed into the prompt alongside them.

    Structural prompting & delimiters

    As a prompt accumulates multiple kinds of content — instructions, retrieved context, examples, the user's actual question — plain paragraphs make it hard for the model to tell them apart. Wrapping each section in clear delimiters fixes that. 

    <rules>
- Only answer using the <context> below.
- If the answer isn't in the context, say so — do not guess.
</rules>

<context>
{retrieved_document_text}
</context>

<question>
{user_question}
</question>

    XML-style tags and Markdown headings both work well for this — the model treats them as strong structural signals, which reduces "instruction drift" (the model quietly ignoring or blending your rules with the content around them).

    A well-structured prompt gets the model reading the right things. Whether it can actually reason its way to a correct answer is a separate problem — and one you can influence directly with how you frame the task.

    Advanced reasoning frameworks

    • Few-shot prompting — showing the model 2-3 worked examples of input → correct output before asking it to do the real one, so it infers the pattern instead of guessing at your intent from a description alone.
    • Chain-of-Thought (CoT) — explicitly asking the model to reason step by step before giving a final answer, which measurably improves accuracy on multi-step problems.
    • Extended reasoning / thinking tokens — newer models (Claude's extended thinking, OpenAI's o-series) can spend an internal reasoning budget before answering; you configure how much, trading latency and cost for accuracy on hard problems.
    Note

    Few-shot and CoT are prompting techniques you write yourself. Extended reasoning is a model capability you turn on via an API parameter — the model does its own step-by-step reasoning internally, separate from the final answer it shows you.

    Every technique so far still assumes you're writing the prompt text by hand. A real application builds prompts out of moving parts — user input, retrieved context, a few examples — and hand-assembling that as a string doesn't scale.

    Dynamic prompt pipelines & templates

    Raw string concatenation ("Answer this: " + user_input + more_text) gets unreadable and error-prone fast, and offers no protection if injected content accidentally contains characters that break your template. jinja2 templates keep prompt structure and injected data cleanly separated. 

    from jinja2 import Template

prompt_template = Template("""
<rules>{{ rules }}</rules>
<context>{{ context }}</context>
<question>{{ question }}</question>
""")

prompt = prompt_template.render(
    rules="Only answer from context.",
    context=retrieved_text,
    question=user_question,
)

    A template that cleanly separates structure from injected data is also your first line of defence against a very real risk: some of that injected data — a user's message, a retrieved document — might not be trustworthy at all.

    Defensive prompting & AI security

    Anything a user (or a retrieved document!) can type is a potential attack surface. Three risks worth designing against from day one:

    • Prompt injection — a user, or text pulled in via RAG, contains hidden instructions trying to override your system prompt ("ignore previous instructions and...").
    • System prompt leaks — a user tricks the model into revealing your private system prompt or internal rules verbatim.
    • Jailbreaks — crafted inputs designed to get the model to bypass its safety or business-logic constraints.
    Careful

    Never treat the system prompt as your only defence. Add an input sanitization layer that strips or flags suspicious patterns (like explicit "ignore instructions" phrasing) before user or retrieved text ever reaches the model.

    Putting it together

    A production prompt isn't one clever sentence — it's an assembled piece of software: rules placed where the model actually attends to them, structure that keeps every part distinct, a reasoning framework suited to the task, a template that builds it safely, and a defensive layer that assumes some of its input is hostile. With prompts this deliberate, the next problem is making the model's output just as reliable — which is exactly where Chapter 4 picks up.

    Common mistakes

    Common mistakes

    • Burying the most important rule in the middle of a long context dump, then being surprised when the model "ignores" it.
    • Mixing instructions, retrieved context, and the user's question together as one wall of text, with no delimiters separating them.
    • Trusting the system prompt alone as a security boundary, with no input sanitization layer behind it.
    Best practices

    Best practices

    • Place your most critical rules at the very start or very end of a long prompt, never buried in the middle.
    • Wrap distinct sections (rules, context, question) in clear tags so the model can tell them apart structurally.
    • Build prompts from templates with named variables, not string concatenation, and sanitize untrusted input before it reaches the model.
    Summary

    Key takeaways

    • The "lost in the middle" effect means position in a long prompt affects how reliably an instruction is followed.
    • Structural delimiters (XML tags, Markdown) reduce instruction drift by making sections distinct.
    • Few-shot examples and Chain-of-Thought are two different levers for improving accuracy.
    • Defensive prompting assumes some input is hostile and sanitizes it before it ever reaches the model.
    Practical

    Practical things you can apply right now

    • Take a prompt you've written as one long paragraph and rewrite it using <rules>, <context>, and <question> tags.
    • Add two or three worked examples to a prompt (few-shot) and compare the output against the same prompt with zero examples.
    • Add "think step by step before answering" to one prompt and check whether the final answer's accuracy changes on a multi-step question.
    • Convert one hard-coded f-string prompt into a jinja2 template with named variables.
    • Write down one sentence a malicious user might type to try to override your system prompt, and test whether your current prompt resists it.
