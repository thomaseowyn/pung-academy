Chapter 5

Grounding AI with Your Data (RAG & Vector Search)

    Learning material

    Chapters 3 and 4 made prompts and outputs reliable. This chapter tackles a different problem entirely: the model simply doesn't know things it was never trained on. No amount of clever prompting fixes that — you have to give it the information directly.

    The RAG architecture

    A model only knows what it saw during training — nothing about your private documents, your product's internal database, or anything published after its training cutoff. Retrieval-Augmented Generation (RAG) fixes this without retraining anything: at query time, you retrieve the most relevant pieces of your own data and insert them directly into the prompt, so the model answers grounded in real, current text instead of guessing.

    Note

    RAG beats fine-tuning for most knowledge tasks because your data can change constantly — update the source documents and the very next query reflects it. Fine-tuning "bakes in" knowledge and needs a fresh, costly retraining pass every time the underlying facts change.

    "Retrieve the most relevant pieces" is doing a lot of work in that sentence. To actually find them, you need a way to measure how close in meaning two pieces of text are — which is exactly what an embedding gives you.

    Embeddings & semantic similarity

    An embedding is a numeric vector representing the meaning of a piece of text — produced by a dedicated model like text-embedding-3-small. Texts with similar meaning end up as vectors that are mathematically close together, so "semantic distance" becomes something you can actually compute. 

    response = client.embeddings.create(
    model="text-embedding-3-small",
    input="How do I reset my password?",
)
vector = response.data[0].embedding   # e.g. a 1536-number list

    This is what makes retrieval "semantic" rather than keyword-based: a query for "reset my password" can match a document about "account recovery" even though they share no exact words, because their embeddings land close together.

    Embeddings compare pieces of text — but "your data" usually arrives as whole documents, not tidy pieces. Getting from one to the other is the next step.

    Document loading & chunking

    Real documents (PDFs, Markdown, web pages) are too long to embed as one giant block — and stuffing an entire document into a prompt wastes tokens on irrelevant parts. Instead, you split each document into smaller, overlapping chunks, each coherent enough to stand alone as a unit of meaning.

    Tip

    Overlap matters: without it, a sentence that spans a chunk boundary gets cut in half, and neither half retrieves well on its own. A small overlap (for example, the last few sentences of one chunk repeated at the start of the next) keeps ideas intact across the split.

    Chunked and embedded documents still need somewhere to actually live — somewhere built to search millions of vectors by similarity, not by exact match.

    Vector databases

    Once documents are chunked and embedded, they need somewhere to live that supports fast similarity search across potentially millions of vectors. A lightweight vector database like ChromaDB or Qdrant stores each chunk's text alongside its embedding, and can return the closest matches to a new query vector in milliseconds. 

    import chromadb

client = chromadb.Client()
collection = client.create_collection("docs")

collection.add(
    documents=[chunk_text_1, chunk_text_2],
    embeddings=[vector_1, vector_2],
    ids=["chunk-1", "chunk-2"],
)

    Every piece is now in place: a way to measure meaning, chunks small enough to retrieve precisely, and somewhere fast to search them. Here's what answering one real user question looks like end to end.

    The full RAG pipeline

    query = "How do I reset my password?"

query_vector = embed(query)
results = collection.query(query_embeddings=[query_vector], n_results=3)
retrieved_chunks = results["documents"][0]

prompt = f"""
<context>
{chr(10).join(retrieved_chunks)}
</context>

<question>{query}</question>
Answer using only the context above.
"""

answer = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": prompt}],
)

    Embed the query, retrieve the top-K closest chunks, inject them into the prompt (Chapter 3's structural prompting applies directly here), and let the model generate its answer grounded in exactly that retrieved text.

    Embed query → Retrieve top-K chunks → Inject into prompt → Generate grounded answer

    The four-step shape of every RAG system, regardless of which vector database or model provider it uses.

    Putting it together

    The model can now answer from documents it never saw during training, kept current simply by updating what's in the vector database — no retraining required. It still only answers one question at a time, though, with no memory of what was asked before and no way to hand off to a more specialized process. Chapter 6 is where the model starts acting less like a single call and more like an ongoing agent.

    Common mistakes

    Common mistakes

    • Chunking without overlap, splitting one idea across a boundary so neither resulting chunk retrieves well.
    • Retrieving too many chunks and stuffing them all into the prompt, triggering Chapter 3's "lost in the middle" problem.
    • Assuming RAG eliminates hallucination entirely, instead of just reducing it by grounding answers in retrieved text.
    Best practices

    Best practices

    • Chunk with a small overlap so ideas spanning a boundary still retrieve correctly from at least one chunk.
    • Retrieve only the top few most relevant chunks (top-K), not everything above a loose similarity threshold.
    • Structure retrieved context clearly in the prompt (Chapter 3's tags), and instruct the model to say when the context doesn't contain an answer.
    Summary

    Key takeaways

    • RAG grounds a model in your own data at query time, without retraining, by retrieving and injecting relevant text.
    • Embeddings measure semantic similarity, enabling retrieval by meaning rather than exact keyword match.
    • Documents are chunked (with overlap) and stored in a vector database for fast similarity search.
    • The pipeline is always: embed the query, retrieve, inject into the prompt, generate.
    Practical

    Practical things you can apply right now

    • Generate an embedding for two similar sentences and two unrelated ones, and confirm the similar pair's vectors are closer together.
    • Take one real document you have and split it into overlapping chunks of a few hundred words each.
    • Stand up a local ChromaDB collection, add your chunks with their embeddings, and query it with a real question.
    • Wire the retrieved chunks into a structured prompt (Chapter 3 style) and generate a grounded answer end to end.
