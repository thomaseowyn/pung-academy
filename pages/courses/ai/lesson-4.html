Chapter 4

Structured Data & Tool Calling (Pydantic v2)

    Learning material

    Chapter 3 made the prompt going in reliable. This chapter does the same for what comes back out — so a model's free-form reply can actually plug into the rest of your program.

    Pydantic v2 fundamentals

    An LLM is non-deterministic; the rest of your software is not. Pydantic is the bridge: define the exact shape of data you expect as a Python class, and it validates (or rejects) anything that doesn't match — with clear type hints, not manual if checks scattered everywhere. 

    from pydantic import BaseModel

class Invoice(BaseModel):
    vendor: str
    amount: float
    is_paid: bool

data = {"vendor": "Acme", "amount": "129.50", "is_paid": False}
invoice = Invoice(**data)   # amount is coerced to float automatically
print(invoice.amount)       # 129.5

    That's the schema half solved. The next question is how to actually get the model to produce data shaped like that in the first place, instead of a paragraph of prose.

    Enforcing structured JSON output

    Both OpenAI and Anthropic support a JSON output mode that guarantees the reply parses as valid JSON. That alone isn't enough — valid JSON can still have the wrong fields or types. Combining JSON mode with a Pydantic schema closes that gap: parse the JSON straight into your model, and any mismatch raises a clear validation error immediately. 

    from pydantic import BaseModel, ValidationError
import json

class Extraction(BaseModel):
    name: str
    age: int

raw = client.chat.completions.create(
    model="gpt-4o-mini",
    response_format={"type": "json_object"},
    messages=[{"role": "user", "content": "Extract: 'Alex is 29 years old' as JSON with name and age."}],
).choices[0].message.content

try:
    person = Extraction.model_validate(json.loads(raw))
except ValidationError as e:
    print("Model returned something unexpected:", e)

    Structured JSON is enough for data extraction — but sometimes you don't just want the model to describe an action, you want it to actually trigger one in your system. That's what tool calling is for.

    Function/tool calling basics

    Tool calling lets you hand the model a list of real Python functions it can "request" — the model never runs your code itself; it only returns which function to call and with what arguments, and your program decides whether and how to actually run it. 

    def get_weather(city: str) -> str:
    return f"It is sunny in {city}."

tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "Get the current weather for a city",
        "parameters": {
            "type": "object",
            "properties": {"city": {"type": "string"}},
            "required": ["city"],
        },
    },
}]

    Executing AI tools

    A tool schema on its own doesn't do anything — it just tells the model what's available. Making it actually run is a loop: the model requests a tool call, your Python code runs the matching function, and the deterministic result is fed back to the model so it can write a final, natural-language answer that incorporates it. 

    response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "What's the weather in Tokyo?"}],
    tools=tools,
)

tool_call = response.choices[0].message.tool_calls[0]
args = json.loads(tool_call.function.arguments)
result = get_weather(**args)   # your own function actually runs, not the model

follow_up = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "user", "content": "What's the weather in Tokyo?"},
        response.choices[0].message,
        {"role": "tool", "tool_call_id": tool_call.id, "content": result},
    ],
)
print(follow_up.choices[0].message.content)
    Tip

    The model chooses which tool to call and what arguments to pass — it never executes anything. That distinction is what keeps tool calling safe: your code stays in full control of what actually runs.

    Putting it together

    The model's output is now something your code can trust: a validated schema instead of free text, and real functions it can trigger instead of just describing what it would do. The next gap is knowledge, not structure — Chapter 5 is about giving the model access to information it was never trained on, so it stops guessing at facts it simply doesn't have.

    Common mistakes

    Common mistakes

    • Trusting JSON-mode output without validating it — JSON mode guarantees valid JSON syntax, not the right fields or types.
    • Letting the model execute a tool's side effects directly, instead of keeping your own code in control of whether it actually runs.
    • Defining a tool schema so vaguely that the model can't reliably tell when it should be used.
    Best practices

    Best practices

    • Always parse structured output through a Pydantic model, even when the provider guarantees JSON syntax.
    • Keep tool execution in your own code — the model requests, your code decides whether and how to run it.
    • Write clear, specific tool descriptions, since that description is how the model decides when to call it.
    Summary

    Key takeaways

    • Pydantic models define expected data shape as type-hinted classes, validating (or rejecting) anything that doesn't match.
    • JSON mode plus Pydantic closes the gap between "syntactically valid JSON" and "the exact shape your code needs."
    • Tool calling lets a model request a function call; your code always decides whether it actually runs.
    • The full loop is request → tool call → execute → feed result back → final answer.
    Practical

    Practical things you can apply right now

    • Define a Pydantic model for one real data shape you work with, and validate a plain dict against it.
    • Turn one of your existing prompts into a JSON-mode call, then parse the result straight into a Pydantic model and see what happens when the model returns something slightly off-shape.
    • Write one plain Python function (no API calls inside it) and describe it as a tool schema.
    • Build the full request → tool call → execute → follow-up loop for that one function, end to end.
