    Learning material

    Why the tooling changed

    This course assumes you can already write Python — variables, functions, loops, classes. What it teaches instead is the layer around that: the tooling, APIs, and architecture that turn "a Python script that calls an LLM" into a production AI system. Chapter 1 sets up an environment worth building on before you write a single line of AI code.

    A 5-minute primer: git and APIs

    Two things get used constantly from here on without being taught from scratch: git and APIs. If you're already comfortable with both, skip straight to the next section — this chapter assumes exactly this much and no more.

    Git is a tool that tracks every change made to a project over time. A repository ("repo") is a project git is tracking; a commit is a saved snapshot of the code at one point, with a short message describing what changed. That history is what makes it safe to try things, undo mistakes, and work alongside other people without overwriting each other's work. 

    git init                        # start tracking this folder
git add .                       # stage every changed file
git commit -m "Initial commit"  # save a snapshot
git status                      # see what's changed since the last commit

    A .gitignore file (used later in this chapter) simply lists files git should never track — most importantly, anything containing a secret.

    An API (Application Programming Interface) is how one program talks to another over the internet — the same basic idea as a browser loading a webpage, except the "visitor" is your code, not a person clicking around. Your program (the client) sends a request to someone else's computer (the server — in this course, OpenAI's or Anthropic's), and gets a response back. Two request types matter most: GET (ask for something) and POST (send something, which is how almost every AI API call in this course works). Both the request and the response are usually written in JSON — the same text-based data format you may already know from reading or writing files.

    Note

    That's the entire primer. Everything from here treats "commit your work" and "send a POST request" as things you can now do without further explanation.

    Next-gen project management with uv

    uv replaces the old pip + venv combination with a single, much faster tool. It creates an isolated virtual environment for every project automatically, resolves and locks dependencies, and installs them fast enough that "just run uv sync" feels instant compared to a traditional pip install -r requirements.txt. 

    uv init ai-course-project
cd ai-course-project
uv add openai anthropic python-dotenv httpx
uv run python main.py
    Note

    uv add installs a package and records it (with an exact resolved version) in the project's lockfile. Anyone who clones the project and runs uv sync gets the identical dependency set — no "works on my machine."

    A locked, isolated environment solves "which packages, which versions" — but a project also needs to stay readable as you (or a team) add to it over time. That's the next habit worth automating.

    Code quality with ruff

    ruff is a linter and formatter in one tool, replacing the old stack of flake8 + black + isort. It catches unused imports, style violations, and common bugs, and reformats code on save when wired into your editor. 

    uv add --dev ruff
ruff check .      # lint the project
ruff format .     # auto-format the project
    Tip

    Configure ruff once in pyproject.toml and set your editor to run it on save. From that point on, consistent formatting stops being something you think about.

    Environment and style are now both handled by tools, not willpower. There's one more piece of hygiene that has to be right from your very first commit, before you write any AI code at all: how you handle the credentials that code will need.

    Secrets management with .env and git

    An LLM API key is a credential, not a string constant — it must never be hard-coded or committed to git. The standard pattern: keep secrets in a local .env file, load them with python-dotenv, and make sure git never tracks that file. 

    # .env  (never commit this file)
OPENAI_API_KEY=sk-...
ANTHROPIC_API_KEY=sk-ant-...
    # .gitignore
.env
.venv/
    from dotenv import load_dotenv
import os

load_dotenv()
api_key = os.environ["OPENAI_API_KEY"]
    Careful

    Add .env to .gitignore before your first commit, not after. A key that ever touches git history should be treated as leaked and rotated immediately, even if you remove it in a later commit.

    With your keys safely loaded and never at risk of being committed, you're ready for the part every other chapter in this course depends on: actually calling a model. That's where one habit from ordinary Python scripting starts to break down.

    Asynchronous Python for API calls

    An LLM API call is high-latency network I/O — your program sends a request and then waits, sometimes for several seconds, before anything comes back. async /await lets your program do other useful work during that wait instead of freezing in place. 

    import asyncio
import httpx

async def fetch_completion(prompt: str) -> str:
    async with httpx.AsyncClient() as client:
        response = await client.post(
            "https://api.openai.com/v1/chat/completions",
            headers={"Authorization": f"Bearer {api_key}"},
            json={"model": "gpt-4o-mini", "messages": [{"role": "user", "content": prompt}]},
        )
        return response.json()["choices"][0]["message"]["content"]

result = asyncio.run(fetch_completion("Say hello"))

    You don't need to master async fully in this chapter — you need enough to recognise the pattern: async def marks a function as awaitable, await pauses it (and only it) until the result is ready, and httpx.AsyncClient is the async-friendly counterpart to a normal HTTP client. The rest of this course builds directly on top of this pattern.

    Putting it together

    Four small pieces, one coherent setup: uv for a fast, isolated, reproducible project; ruff to keep the code inside it consistent; .env to keep every credential out of git; and async/await so your program doesn't stall every time it waits on a model. None of this is AI-specific by itself — but every chapter from here on assumes it's already in place. Chapter 2 puts it to work on the first real API call.

    Common mistakes

    Common mistakes

    • Installing packages globally instead of into an isolated project environment, so different projects silently fight over dependency versions.
    • Writing a .gitignore after the first commit instead of before it — by then a secret may already be in git history.
    • Reaching for async/await everywhere out of habit, even around code that never actually waits on anything (like pure computation) — it adds complexity with no benefit there.
    Best practices

    Best practices

    • Start every new project with uv init before writing any code, so dependencies are tracked from line one.
    • Create .gitignore in the very first commit, before any secret has a chance to be tracked.
    • Reserve async/await for genuinely I/O-bound work — API calls, file access, database queries — not CPU-bound logic.
    Summary

    Key takeaways

    • uv replaces pip + venv with one fast tool that locks exact dependency versions.
    • ruff lints and formats in one tool, keeping code style consistent automatically.
    • Secrets belong in .env, which belongs in .gitignore from the very first commit.
    • async/await lets a program keep working while it waits on high-latency network calls, like every LLM API request in this course.
    Practical

    Practical things you can apply right now

    • If git init, git add, and git commit are new to you, run all three on any folder right now, then make one more change and commit it again.
    • Install uv, then run uv init on a fresh folder and add openai, anthropic, python-dotenv, and httpx to it.
    • Add ruff as a dev dependency and run ruff format . against any existing script you have lying around.
    • Create a .env and a .gitignore in that project before writing any API key into it, and confirm git status never shows .env as trackable.
    • Take one function you already have that calls an external API with requests, and rewrite it using async def/await and httpx.AsyncClient.
