Chapter 6

Agentic Workflows & Memory

    Learning material

    Chapter 5 gave the model access to your data. This chapter gives it something else it's been missing: a memory of the conversation so far, the ability to hand off to a specialist when a request isn't its job, and a way to recover when its own output goes wrong.

    Conversational memory

    Every chapter so far has sent one prompt and read one reply. A real conversation needs memory: the growing list of past messages, resent with every new request so the model has the full thread of context. 

    history = [{"role": "system", "content": "You are a helpful assistant."}]

def ask(user_message: str) -> str:
    history.append({"role": "user", "content": user_message})
    reply = client.chat.completions.create(model="gpt-4o-mini", messages=history)
    text = reply.choices[0].message.content
    history.append({"role": "assistant", "content": text})
    return text

    Left unmanaged, that history array grows without bound — and every past message gets resent (and rebilled) on every new call, eventually overflowing the model's context window (Chapter 2). Long-running sessions need a strategy: truncate the oldest messages, or periodically summarize the older half of the conversation into a short recap and replace it in place.

    Memory keeps one agent coherent across a conversation. The next problem shows up once that agent is expected to handle more than one kind of request well.

    Multi-agent routing

    As an application takes on more kinds of requests, one giant system prompt trying to handle everything gets unwieldy and inconsistent. A router agent solves this by doing one job only: classify what the user actually wants, then forward the request to a specialized sub-agent built for that exact task. 

    def route(user_message: str) -> str:
    classification = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system", "content": "Reply with exactly one word: 'data' or 'chat'."},
            {"role": "user", "content": user_message},
        ],
    ).choices[0].message.content.strip().lower()

    if classification == "data":
        return extraction_agent(user_message)
    return conversational_agent(user_message)
    User message → Router agent
    (classifies intent)     → Extraction agent Conversational agent

    The router's only job is classification and handoff — each sub-agent can have its own prompt, tools, and model.

    Note

    Each sub-agent can have its own system prompt, its own tools (Chapter 4), and even its own model — a fast, cheap model for simple chat, a stronger one for complex extraction — instead of one expensive model handling every request identically.

    Routing handles which agent should answer. It doesn't handle what happens when the agent that does answer produces something malformed — which, with structured output (Chapter 4), will eventually happen.

    Error handling & self-correction

    Chapter 4 showed Pydantic raising a ValidationError when a model's JSON doesn't match your schema. A resilient agent doesn't just crash on that error — it feeds the exact error text back to the model and asks it to fix its own output. 

    from pydantic import ValidationError
import json

def get_structured_reply(prompt: str, schema, attempts: int = 2):
    for attempt in range(attempts):
        raw = client.chat.completions.create(
            model="gpt-4o-mini",
            response_format={"type": "json_object"},
            messages=[{"role": "user", "content": prompt}],
        ).choices[0].message.content
        try:
            return schema.model_validate(json.loads(raw))
        except ValidationError as e:
            prompt = f"{prompt}\n\nYour previous output failed validation with this error:\n{e}\nReturn corrected JSON only."
    raise RuntimeError("Model could not produce valid output after retries.")
    Tip

    This self-correction loop works because the model is genuinely good at reading an error message and fixing the specific thing that was wrong — far better than it is at guessing your schema correctly with zero feedback.

    Putting it together

    An agent that remembers the conversation, routes to the right specialist, and corrects its own mistakes is genuinely close to a real product — everything so far has run as a script, though. Chapter 7 puts it behind a real web server so an actual frontend can use it.

    Common mistakes

    Common mistakes

    • Letting conversation history grow forever, eventually overflowing the context window and rebilling every past message on every call.
    • Building one giant system prompt trying to handle every kind of request instead of routing to specialized sub-agents.
    • Retrying a failed structured-output call with the exact same prompt, giving the model no new information to correct itself with.
    Best practices

    Best practices

    • Truncate or summarize older messages once history grows past a reasonable length.
    • Give each specialized sub-agent its own prompt, tools, and even model — don't force one model to do everything equally well.
    • Feed the exact validation error back into the retry prompt, so the model has something concrete to fix.
    Summary

    Key takeaways

    • Conversational memory is a growing list of messages resent on every call; it needs a truncation or summarization strategy for long sessions.
    • A router agent classifies intent and hands off to specialized sub-agents, rather than one model doing everything.
    • Self-correction feeds a specific error back to the model, which is far more effective than a blind retry.
    Practical

    Practical things you can apply right now

    • Build a small chat loop that keeps a growing history list and actually holds a multi-turn conversation.
    • Add a simple truncation rule that drops the oldest messages once the history passes a fixed length.
    • Write a one-call classifier that routes a message to either of two different system prompts based on its content.
    • Wrap one of your Chapter 4 structured-output calls in a retry loop that feeds a validation error back to the model.
