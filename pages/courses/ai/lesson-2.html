Chapter 2

The LLM API Layer (OpenAI & Anthropic)

    Learning material

    Chapter 1 got your environment, credentials, and async pattern ready. This chapter is where that setup finally does something: your first real, authenticated call to a model.

    The Chat Completions API

    Both OpenAI and Anthropic expose their models through a similar shape of API: you send a list of messages, each tagged with a role, and get a generated reply back. Three roles matter most:

    • system — instructions that set the model's behaviour for the whole conversation (tone, rules, persona).
    • user — what the person actually asked.
    • assistant — the model's own previous replies, included so it has conversational memory.
    from openai import OpenAI

client = OpenAI()

response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": "You are a concise coding assistant."},
        {"role": "user", "content": "What does len() do in Python?"},
    ],
)

print(response.choices[0].message.content)

    Anthropic's Messages API follows the same idea, with the system prompt passed as its own top-level parameter rather than a message: 

    from anthropic import Anthropic

client = Anthropic()

response = client.messages.create(
    model="claude-sonnet-4-5",
    system="You are a concise coding assistant.",
    max_tokens=300,
    messages=[{"role": "user", "content": "What does len() do in Python?"}],
)

print(response.content[0].text)

    Getting a reply back is the easy part. The more useful skill is controlling what kind of reply comes back — and that's a mix of how you build the prompt itself and which generation parameters you dial in alongside it.

    Programmatic prompt engineering

    Real applications build prompts dynamically — injecting a user's actual input, retrieved data, or prior context into a template — rather than hard-coding a fixed string. Three parameters shape how the model generates from whatever prompt it receives:

    • temperature — how much randomness to inject when picking the next token. Low (near 0) is deterministic and repeatable; higher values add variety.
    • top_p — an alternative way to control randomness, by only sampling from the smallest set of tokens whose combined probability reaches p.
    • max_tokens — a hard cap on how long the generated reply is allowed to be.
    Note

    Most teams adjust temperature or top_p, not both at once — changing both makes it much harder to reason about why an output changed.

    Those parameters control the content of the reply. The next question is about how that reply actually reaches the user — and whether they have to stare at a blank screen while the whole thing generates.

    Streaming responses

    By default, an API call waits for the entire reply to finish generating before returning anything. Streaming instead delivers the reply chunk by chunk, as each new token is produced — the same effect you see as the "typing" animation in ChatGPT or Claude. 

    stream = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Write a haiku about Python"}],
    stream=True,
)

for chunk in stream:
    delta = chunk.choices[0].delta.content
    if delta:
        print(delta, end="", flush=True)

    Every one of these calls — streamed or not, at any temperature — has a cost attached, and a hard ceiling on how much text it can involve. That's worth understanding before you build anything that makes these calls in a loop.

    Token economics & logging

    Every API call is billed by tokens: roughly, pieces of words, counted separately for the input you send and the output the model generates. Each model also has a fixed context window — the maximum number of input + output tokens it can handle in one call. Going over it causes the request to fail outright. 

    usage = response.usage
print(usage.prompt_tokens, usage.completion_tokens, usage.total_tokens)
    Tip

    Log the raw API response (not just the extracted text) during development. When something goes wrong, the raw response — including usage, the finish reason, and any errors — is usually where the actual answer is.

    Putting it together

    You can now talk to both major providers directly, shape their output with real parameters, stream it live, and track what it's costing you. That's a working API layer — but every prompt so far has been a single hard-coded string. Chapter 3 is about designing that prompt itself like a piece of software, not an afterthought.

    Common mistakes

    Common mistakes

    • Leaving temperature at a high default for tasks that need consistent, repeatable output, like data extraction.
    • Not setting max_tokens, letting a runaway generation cost far more than intended.
    • Building a chat UI without streaming, forcing users to stare at a blank screen for the entire generation time.
    Best practices

    Best practices

    • Match temperature to the task: near 0 for extraction/classification, higher for creative or conversational replies.
    • Log the full raw response (including usage) during development, not just the extracted text.
    • Stream any reply a user waits on directly, so perceived latency drops even when total generation time doesn't.
    Summary

    Key takeaways

    • system/user/assistant roles shape a conversation; system sets standing behaviour, assistant carries memory of prior replies.
    • temperature, top_p, and max_tokens control randomness and length of generation.
    • Streaming delivers a reply chunk by chunk instead of waiting for the whole thing to finish.
    • Every call is billed by tokens, with a hard context-window ceiling per model.
    Practical

    Practical things you can apply right now

    • Make one real Chat Completions call with a system and a user message, and print the raw response object before extracting just the text.
    • Run the same prompt twice at temperature=0, then twice at a higher value, and compare how much the output actually changes.
    • Convert a non-streaming call into a streaming one, and print each chunk as it arrives instead of the final result.
    • Print response.usage on a real call and calculate its approximate cost using your model provider's published per-token pricing.
